# Sentinel evaluation: rules vs agent vs hybrid

123 synthetic scenarios (43 scam timelines, 80 benign user-weeks; English, Hindi, Hinglish) replayed
through the real pipeline (`process_event`, Postgres, alert policy). Rules were tuned on the `tune`
split only. `holdout` was first run once, after tuning. The rerun after the R34 fix below changed
no rules.

## Headline (hybrid, the default mode)

| split | scam recall (alert >= high before the pay/OTP/remote-access step) | false interrupts per user-week | gate |
|---|---|---|---|
| tune (29 scams / 55 weeks) | 29/29 = 1.000 | 0.018 | pass |
| **holdout (14 / 25)** | **12/14 = 0.857** | **0.160** | **pass, but only just; see the note below** |
| all (43 / 80) | 41/43 = 0.953 | 0.062 | pass |

**Read the holdout pass with care.** The first holdout run (120 scenarios) gave 11/13 = 0.846, and the
gate FAILED. Since then three contact-name-spoofing scams were added (R34 fix below). One of them is
easy, it fell into holdout and it is caught. The same two holdout scams are still missed. On the
original 13 holdout scams, recall is still 11/13 = 0.846. The pass comes from adding scenarios, not
from better detection.

Before tuning (original tune split): rules 21/27 = 0.78, agent 22/27 = 0.81, hybrid 22/27 = 0.81
recall; 0.13 false interrupts per user-week in all three modes.

## R34 fix: explicit `is_contact` replaces display-name contact inference

Tuning change #6 (below) inferred a saved contact from the *shape* of a WhatsApp display name. A
security review found an attacker could name themselves "Mom" to suppress `unknown_sender`. That
inference is removed. `EventIn` has an optional, client-checked `is_contact`: the app sets it from
`ContactsContract` / the notification's contact URI; omitted means unknown, as before. Only
`is_contact: true` suppresses `unknown_sender`. The scenarios were regenerated deterministically:
27 files gained `is_contact: true` on saved-contact family WhatsApp messages and nothing else
changed. No existing scenario changed split. Three scams were added (`contact_name_spoof`: "Mom",
"Papa", "Bank Manager" senders with `is_contact` false or omitted), with their own RNG and split
stream. The tune split showed no side effect, so no rule was recalibrated. Caveat: all three spoof
scams carry enough content risk (payment or OTP ask plus urgency) to reach `high` even without
`unknown_sender`, so they do not tell old and new behaviour apart. The unit tests in
`tests/test_signals_calibration.py` carry that guarantee.

## What the ablation shows (and does not)

- With the scripted fake agent, the three modes have the **same recall and the same false
  interrupts**. The tuned rules already reach `high` on every scam they catch. The agent's
  tool-confirmed raises change **severity**, not detection: in-time warnings that are `critical`
  rise from 0.49 (rules) to 0.59 (hybrid) overall, from 4 events where tools confirmed a <7-day
  domain plus a payment/OTP ask, or a threat-feed hit. In `agent` mode (no rules floor) the fake
  agent cleared one benign caution after verifying a clean link (caution/week 0.59 -> 0.57).
- Before tuning, hybrid/agent caught one scam that rules missed (a UPI collect scam), which is the
  memory + tools differentiator at work; after tuning, rules catch it too.
- **The agent column measures plumbing, caps and the floor, not model quality.** `--llm fake` is a
  deterministic script that follows tool facts; a real model was not run (no Token Factory key).
  Run `--llm live` to get a real agent column.

## Tuning changes (tune split only)

All in `app/pipeline/signals.py` unless noted, each pinned by `tests/test_signals_calibration.py` with
benign counter-examples; all pre-existing tests unchanged and green.

| # | change | why (tune failure) | tune effect |
|---|---|---|---|
| 1 | BUG fix: Hindi deposit ask `जमा करें` failed before a danda `।` (the lookahead excluded the whole Devanagari block, which contains U+0964/5) | `scam-investment-group-02` ("... खाते में जमा करें।") scored info | missed -> caught |
| 2 | `payment_request`: pay / send / transfer / bhej / invest to a UPI id, either order ("x@ybl pe bhej do", "x@okaxis पर भेजें") | `scam-investment-group-03`, `scam-job-task-02` | 2 missed -> caught |
| 3 | `payment_request`: fee asks ("pay registration fee", "शुल्क देकर"), not "pay on delivery" | `scam-job-task-04`, `scam-courier-customs-02` | 2 missed -> caught |
| 4 | `credential_or_otp_ask`: Hinglish PIN entry ("UPI PIN daal do / dalo") | `scam-upi-collect-03` (rules mode) | caught in rules too |
| 5 | `channel_hop`: a bank / brand org seen on another channel is not a hop; claims and impersonated authorities (CBI, RBI, TRAI, customs, police) still are | `benign-card-statement-03`: ICICI SMS then ICICI e-statement email -> high | false interrupt removed |
| 6 | ~~`unknown_sender`: a WhatsApp plain display name counts as a saved contact~~ **REMOVED in R34** (spoofable: an attacker can name itself "Mom"). Replaced by the client-checked `EventIn.is_contact`; family-chat scenarios now carry `is_contact: true` | `benign-family-chat-01/06`: "send ₹1,200" from "Mummy" as the first message of the week | the 2 false interrupts stay removed (via the flag) |
| 7 | `tools.py`: Amazon's own short domains `amzn.in`, `amzn.to`, `amzn.eu` are not Amazon lookalikes | `benign-delivery-updates-01/03/06` | 3 false interrupts removed |
| 8 | fix of my own regression in #3: "Pay on delivery amount Rs ..." is not an ask | `benign-delivery-updates-03/05` after round 1 | 2 false interrupts removed |

Harness fix after the holdout run (no rules change): the scripted fake agent answered `high` on weak
tool facts even when the rules said `critical`, so agent mode (no floor) showed critical -> high
downgrades. It now never argues a confirmed risk down. Recall / interrupts were unaffected (both tiers
interrupt).

Task 7's parked Hindi payment-notification exemption (R23) did not show up in any failure, so it was
not changed.

## Holdout failures (not tuned on)

None is a clear code bug; all are heuristic gaps, listed for the next iteration:

- `scam-job-task-03` (Hinglish): the ask is "19,000 rupees ka recharge karo" (no pay/send verb), and the
  earlier task-site link was never escalated (rules saw info and device triage was 0.4 < 0.5), so RDAP
  and the agent never ran.
- `scam-sextortion-03` (Hindi): "अगर ₹6,500 नहीं भेजे तो ..." puts the amount before a negated verb and
  "किसी को बताया तो" is a threat, not a "don't tell" phrasing: no payment or secrecy signal.
- `benign-adversarial-benign-07`: an awareness SMS ("Cyber Crime Awareness: never ... install screen
  sharing apps like AnyDesk") fires authority + remote access from a first-seen header.
- `benign-delivery-updates-04` (and tune `-06`): Amazon's "Share OTP 1234 with the delivery agent"
  SMS is a credential ask by the rules; with a first-seen header or 3 Amazon messages in 72 h it
  reaches high.
- `benign-upi-confirmations-02/05` (Hindi): bare `भुगतान` ("payment") fires on PhonePe's past-tense
  "भुगतान सफलतापूर्वक किया" confirmations (the same class as the parked English "transfer" alerts);
  with the app shown as a first-seen sender it reaches high.

## Caveats

- **Synthetic data, optimistic numbers.** All scenarios come from a seeded template generator written
  by the same team / agent that tuned the rules, with knowledge of the rules. Tune recall of 1.000 is
  overfitting to our own templates; the holdout (same templates, new slot values) is only a mild
  check. Real traffic will be worse. No human has reviewed the scenarios yet (20 suggested in
  `eval/README.md`).
- **Small holdout.** 14 scams: one scenario moves recall by about 0.07 (see the holdout note above).
- **`is_contact` is client-asserted.** Its value depends on the app setting it only after a real
  contacts lookup, never from a display name.
- **Fake agent.** See above; the agent numbers are not model-quality numbers.
- **Fresh users.** Every scenario starts with empty history, so first contacts from banks and apps
  count as unknown senders; real users have weeks of history (fewer false interrupts), but scammers
  also get fewer memory hits in a fresh account than the slow-burn timelines show.
- **Offline fixtures.** Domain ages and link-inspector reports are scenario fixtures, not live RDAP /
  sandbox results; about 20% of scam links are deliberately "down" (unfetched).
- Latency is in-process on a laptop with no network calls (RDAP / inspector / LLM are instant
  fixtures); production latency will be dominated by those calls.
