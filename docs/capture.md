# Always-on capture (Android)

Sentinel reads notifications of a fixed list of apps and, if the user opts in, call metadata. Everything is masked on
the phone before it is queued or sent. Code: `android/app/src/main/java/ai/enthral/sentinel/capture/` and `sync/`.

```
allowlisted notification ─▶ filter ─▶ extract ─▶ truncate 10 000 ─▶ REDACT (on phone) ─▶ sender policy
        ─▶ de-dupe / rate limit ─▶ encrypted outbox ─▶ POST /v1/events (fast path, then WorkManager)
        ─▶ alert? high/critical → heads-up · caution → Alerts tab · follow-ups at +15/+45/+120 s
call ends ─▶ PHONE_STATE idle ─▶ +5 s CallLogSyncWorker ─▶ new CallLog rows ─▶ outbox ─▶ …
call rings (opt-in) ─▶ CallScreeningService: ALLOW at once ─▶ outbox ─▶ expedited drain ─▶ "Possible scam caller"
```

## What is captured

| Source | When | What leaves the phone |
|---|---|---|
| Notifications (consent "Notifications" + Android Notification access) | every new notification of an **allowlisted** app | `source` (sms / whatsapp / email / notification), `ts`, `sender`, masked `text` (≤ 10 000 chars), `triage_score`, `lang`, `is_contact`, `device_event_id` |
| Call log (consent "Call info" + READ_CALL_LOG) | 5 s after each call ends, when the app process starts or Call info is turned on, and every 15 min | `source=call`, `ts` (call time), `sender` = E.164 number (for a **saved contact** the pseudonym `c_<8 hex>` instead, see Sender policy; hidden numbers: none), `call{number, duration_s, is_contact, direction}`, `triage_score=0`, `device_event_id`. No text. |
| Ringing calls (opt-in "Check callers while ringing", ROLE_CALL_SCREENING) | when an incoming call starts ringing | as a call-log event with `duration_s=0`, `direction=in` |

Allowlist (`capture/CaptureAllowlist.kt`, mirrored in the manifest `<queries>` and checked by a unit test):
SMS apps (Google Messages, AOSP/Motorola/Samsung/OnePlus messaging) → `sms`; WhatsApp and WhatsApp Business →
`whatsapp`; Gmail, Outlook → `email`; Telegram, Google Pay, PhonePe, Paytm, BHIM, CRED, Amazon, MobiKwik, Freecharge
and the main Indian bank apps → `notification`. Every other app is dropped by package name before a single extra is
read. Debug builds also accept `com.android.shell` (for `adb shell cmd notification post`); that entry lives in
`src/debug` only and the string is absent from release APKs.

Ignored even for allowlisted apps: Sentinel's own notifications, ongoing / foreground-service notifications, group
summaries, categories call / missed_call / transport / progress / service / status / alarm / sys / navigation /
stopwatch / location_sharing / workout, media and progress notifications, and empty text.

Text: big text, else inbox lines, else text. For MessagingStyle (WhatsApp, Messages) only messages newer than the
last one seen in that conversation are sent (cursor per hashed `package|conversation`), joined in one event.
Payment/bank app titles are headings ("Money received"), so they go into the text and `sender` stays empty.

## What is never captured

Notifications of any other app; chat history; anything before consent or while paused; contact names (see below);
the contact list; call audio or content; SMS through SMS permissions (none are requested); photos, files.
Nothing raw is persisted: the outbox only ever holds the masked `EventIn`. Nothing is logged (no text, titles,
senders, numbers or tokens; see "Testing" for the logcat check).

## Privacy rules (enforced in code and tests)

* **Redaction on the phone** (`Redactor.kt`): a port of `backend/app/pipeline/redact.py` — `[OTP] [CARD] [ACCT]
  [AADHAAR] [PAN]`; phone numbers, URLs, UPI ids and amounts kept as evidence; Devanagari digits; the same
  precedence and fail-closed Aadhaar rule. `RedactorParityTest` asserts byte-identical output with the real Python
  redactor on 593 golden cases (`android/scripts/gen-redact-golden.py`: every literal of `test_redact.py`, ~250
  hand-written bank/courier/Hindi/Hinglish/card/Aadhaar/PAN/phone/amount/injection/degenerate cases, generated
  shapes, and every output again for idempotence). No intentional differences. To match Python's Unicode `re` the
  port spells out `\d` as `\p{Nd}`, `\s` as Python's `isspace()` set, `\b` as lookarounds, the four extra
  IGNORECASE letters, and emulates `search(pos, endpos)` bounds. Caveat: the parity test runs on the JVM; Android's
  ICU regex engine is expected to behave the same for these patterns but is not separately parity-tested.
* **Sender policy** (`SenderPolicy.kt`): phone numbers and operator SMS headers (`VM-HDFCBK`) are sent as they are.
  A name that is, or may be, a saved contact becomes `c_<8 hex of HMAC-SHA256(per-install key, name)>`; without
  READ_CONTACTS names fail closed to the pseudonym. Other names (e.g. an unknown Telegram display name) are sent,
  capped at 200 chars. The HMAC key is random per install, encrypted with the Keystore, and regenerated by
  "Delete my data" (pseudonyms cannot be linked across a wipe).
* **Call numbers of saved contacts**: when the exact E.164 match below proves the number is a saved contact, the number
  is NOT sent. `sender` and `call.number` carry `c_<8 hex of HMAC-SHA256(same per-install key, E.164 number)>` and
  `is_contact=true`; the ringing-call `device_event_id` is derived from the pseudonym, never the number. The key is
  reset by "Delete my data" like the name pseudonyms. Unknown numbers (and numbers when READ_CONTACTS is missing, so
  nothing is proven) are still sent as E.164; hidden numbers as empty. The backend tolerates the non-phone
  `call.number` (`CallMeta.number` is a plain string; entity extraction finds no phone in `c_xxxxxxxx`, checked
  with 20 000 random values), so a contact's number simply produces no phone entity.
* **is_contact** is `true` only when proven: a single-contact lookup uri `contacts/lookup/<key>/<id>` (not a
  display-name-derived key) that resolves to exactly one contact with that `_ID`, or a phone number whose
  PhoneLookup hit normalises to the **same E.164 number** (PhoneLookup itself matches loosely by trailing digits).
  A display name never sets it; groups are always `false`; without READ_CONTACTS it is `null` (calls: `false`,
  the schema needs a boolean). Bare `contacts/<id>`, collection, foreign-authority, malformed or escaped uris are
  never proof.
* **Encryption at rest**: the outbox is one AES-256-GCM blob (Android Keystore key `sentinel_outbox_key`) written
  atomically (temp file + rename) under `noBackupFilesDir`; max 500 items (oldest dropped), 7-day TTL; an unreadable
  file restarts the queue empty instead of crashing. Counters and cursors (hashed keys only) live in a DataStore.
  The caller's number for a ringing call goes straight into the encrypted outbox, never into WorkManager's database.

## Sending, alerts and follow-ups

* Fast path: right after queueing, a coroutine drains the outbox (50 s per request, OkHttp read timeout 45 s: on the
  live server escalated events took 20-35 s, measured on the test phone; with the brief's 20 s they were cancelled).
  If an answer is still too slow, nothing is lost: the retry gets `duplicate: true` and the follow-ups below fetch the
  alert (observed on the phone: critical heads-up ~12 s after the retry).
  Whatever is left goes to `EventSyncWorker` (unique, CONNECTED, exponential backoff from 30 s). One drain at a
  time; `device_event_id` = SHA-256 of `package|key|postTime|masked text` (MessagingStyle: newest message time;
  calls: `call|rowId|date`), so retries are idempotent (`duplicate: true` from the server counts as delivered).
* Errors: 401 → re-register once and retry (DeviceSession); 413 / 422 / other 4xx → dropped and counted; 429 →
  back off 60 s; 408 / 5xx / network / timeout → retry later. Nothing is sent before onboarding finishes.
* Alerts in responses: high/critical → heads-up on `alerts_critical` / `alerts_high` with the server's headline and
  next step, deep link `sentinel://alert/<id>`; caution → no notification (Alerts tab). Ids already notified are
  persisted (shared with the Alerts screen) so an alert never notifies twice. For a ringing call the title is
  "Possible scam caller".
* Late upgrades (stage-2 background review creates a new, higher alert): after any successful send, one-time
  `FollowUpWorker`s at +15 s, +45 s and +120 s (the server answers with a rules alert at once and refines or upgrades it via the background agent in ~20-40 s) call `GET /v1/alerts?since=now-15min` and notify new high/critical ones.
* Budget: max 20 events per package per 10 minutes (sliding) and de-duplication of the same package+key+text within
  10 minutes; `triage_score` (`Triage.kt`) needs two different kinds of cue to reach the server's 0.5 agent gate.

## Gating

Capture runs only when onboarding is finished, the source's consent is on, the OS permission is granted and
"Pause protection" is off. The gate is checked on every notification and call, so Pause and consent changes act
immediately. Call screening needs the Call-info consent but not READ_CALL_LOG.

## Permissions and why

| Permission | Why | Asked |
|---|---|---|
| Notification access | read allowlisted notifications | onboarding / Settings (system screen) |
| READ_CONTACTS | yes/no "is this sender saved" (never names) | with Notifications, and with Call info |
| READ_CALL_LOG | number, time, duration, direction of calls | Call info |
| READ_PHONE_STATE | notice that a call ended | Call info |
| ROLE_CALL_SCREENING | see the number while it rings (never blocks) | Settings opt-in (Android 10+) |
| RECEIVE_BOOT_COMPLETED | re-arm the 15-minute catch-up | install |
| REQUEST_IGNORE_BATTERY_OPTIMIZATIONS | let the user exempt Sentinel | onboarding / Settings row |
| POST_NOTIFICATIONS | heads-up alerts | onboarding / Settings |

## Reliability, battery and OEM notes

* No foreground service: the notification listener is bound by the system while access is granted, which keeps the
  process alive without a persistent notification. A foreground service would add a permanent notification and an
  FGS type that does not fit (`specialUse` needs Play justification) without improving delivery. The expedited
  screening job runs as a short foreground job only on Android < 12 (WorkManager requirement).
* `onListenerDisconnected` → `requestRebind`. `BootReceiver` (BOOT_COMPLETED, MY_PACKAGE_REPLACED) and app start
  re-arm the 15-minute `PeriodicSyncWorker` (call-log catch-up, outbox flush, missed alerts).
* Battery optimisation exemption is offered in onboarding (once Notifications is chosen) and in Settings with a
  status row. OEM killers (Xiaomi, Oppo, Vivo, some Motorola builds) may still stop background work; the Home card
  shows "Needs notification access" when Android revokes access, and Settings shows the last capture time.
* Ringing-call warnings need the network round trip (and possibly the agent) to finish while the phone rings; a
  slow answer still produces the alert, just after the call.

## Call-log backfill

First run (no stored cursor): only calls from the last **6 hours**, at most the **30 newest** (older ones are dropped,
the cursor moves past them). Later runs read rows newer than the cursor, never more than 7 days back, uncapped.

## Limits

* Family push: there is no Firebase, so guardians are **not** notified of the protected person's alerts in real time;
  they see them only via the backend when it supports it.
* Only notifications posted while Sentinel is connected are seen (no backfill of existing notifications).
* WhatsApp/Telegram calls and messages from apps outside the allowlist are not captured.
* Text is truncated to 10 000 chars; an MessagingStyle update that replaces history without new timestamps is
  treated as nothing new.
* The parity test proves JVM behaviour; on-device regex behaviour is expected identical but not separately tested.
* A ringing call and the later call-log row of the same call: the log row is skipped when screening already reported
  that number within 2 minutes (the server does not use duration, so nothing is lost and the call is not counted
  twice).

## Manual test with another phone

`android/scripts/watch-capture.sh` (debug build only) shows what capture does, live, as counters and event types:
`captured source=sms chars=141 masked=0 is_contact=false triage=0.3`, `dropped reason=Duplicate`,
`sent source=sms duplicate=false tier=critical`, `send_failed status=network`, `queue size=0`, `notified tier=critical`,
`follow_up alerts=4 new_loud=1`, `call_log rows=1 queued=1`. It never shows message text, titles, senders or numbers:
the app logs none (tag `SentinelCapture`, compiled out of release builds) and the script additionally suppresses any
line that is not an event word followed by plain `key=value` tokens. Ctrl+C prints totals.

1. Phone A (protected): debug build installed, onboarding done with **Notifications** and **Call info** on, Android
   Notification access granted, alert notifications allowed. Plug it in and run
   `ANDROID_SERIAL=<A> android/scripts/watch-capture.sh`.
2. From phone B, send phone A an **SMS**: `Your parcel is held. Pay Rs 49 redelivery fee at http://parcel-redeliver.in/pay`.
   Expect `captured source=sms` within a second, then `sent ... tier=none|caution|high|critical` (up to ~35 s when
   the agent runs). Send it again: `dropped reason=Duplicate`.
3. Send a **WhatsApp** message from B: `This is a customs officer. Pay Rs 25,000 penalty to customs.clear@ybl or face
   arrest. Do not tell anyone.` Expect `captured source=whatsapp ... is_contact=false` (true only if B is a saved
   contact *and* WhatsApp attached its contact uri), then `sent ... tier=high|critical` and `notified tier=...` with a
   heads-up "Sentinel alert · Critical" on A. If B is a saved contact its name is sent only as `c_<8 hex>`.
4. Send an OTP-like SMS (`Your OTP is 482913`): `captured ... masked=1`, `sent ... tier=none`, no heads-up.
5. **Call** A from B, let it ring, hang up. ~5 s later: `call_log rows=1 queued=1`, `captured source=call
   direction=missed|in`, `sent source=call`. With "Check callers while ringing" on (Settings; Android asks to make
   Sentinel the caller ID & spam app), a `captured source=call ... ringing=true` appears while it rings and, for a
   high/critical answer, a "Possible scam caller" heads-up; the later call-log row is skipped (no double count).
6. Turn on Settings → Pause protection and repeat step 2: `dropped reason=Gated`.
7. Afterwards: Settings → Delete my data; turn the Notification access off; give the call-screening role back to
   the previous app (Android Settings → Default apps → Caller ID & spam app).

## Testing

Unit tests (`./gradlew testDebugUnitTest`): `RedactorParityTest`, `NotificationFilterTest`, `SenderPolicyTest`
(pseudonyms, is_contact, uri accept/reject table, E.164 near misses, key reset, concurrent reset), `OutboxTest`,

ringing priority), `CapturePipelineTest` (gating, masking on disk, dedupe, idempotent ids, truncation, rate limit,
MessagingStyle, hostile inputs), `CallCaptureTest`.

On a phone with the debug build (`-PsentinelApiBaseUrl=https://…`), after onboarding with Notifications on and
Notification access granted:

```bash
export ANDROID_SERIAL=<serial>
adb shell cmd notification post -S bigtext -t 'VM-HDFCBK' otp1 'Your OTP is 482913. Do not share it with anyone. -HDFC Bank'
adb shell cmd notification post -S bigtext -t '+917700112233' story1 'Your BlueDart parcel is held at the depot due to an incomplete address. Call 9876543210 or visit http://bluedart-redelivery.in to reschedule.'
adb shell cmd notification post -S bigtext -t '+919876543210' story3 'This is a customs officer. Your parcel is seized with illegal items. Pay Rs 25,000 penalty immediately to customs.clear@ybl or face arrest. Do not tell anyone.'
adb logcat -d | grep -v adbd | grep -c 482913     # must print 0 (adbd echoes your own command line)
android/scripts/watch-capture.sh --dump           # what happened, counters only
adb shell cmd notification cancel <tag> <id>      # or clear them from the shade
```
Settings → Notification capture shows the counters; Home shows "watching N apps · last event … · queue N".

## Alert detail freshness

Opening an alert detail shows the cached copy immediately, then reloads `GET /v1/alerts` and shows the latest version (a refined alert keeps its id, so its headline/tier can change). A refined alert never notifies again: notified alert ids are remembered.
